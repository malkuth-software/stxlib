# Board checklist: x86-64 (UEFI)

The image is `stxlib-amd64.img` (`appliance/vm/amd64_image.sh`): the VM's
GPT layout in 1 GiB, with FreeBSD's amd64 `loader.efi` as
`EFI/BOOT/BOOTX64.EFI`, the `STXLIB-AMD64` kernel, and the base programs of
the release's amd64 `base.txz`. The QEMU q35 + OVMF boot in
`amd64_image.sh --boot` is the reference machine. No physical x86 board has
booted it yet.

## What a board must offer

| Item | Requirement | Why |
|---|---|---|
| Firmware | UEFI, booting removable media's `EFI/BOOT/BOOTX64.EFI`; no CSM/BIOS boot | only the ESP's loader is installed |
| Secure Boot | off | `loader.efi` is FreeBSD's, unsigned |
| Ethernet | a NIC GENERIC drives: em, igb, igc, ix, re, vtnet and the others GENERIC lists | the kernel keeps GENERIC's drivers (`STXLIB-AMD64` header) |
| Storage | NVMe (`nda`), SATA/AHCI (`ada`), USB mass storage (`da`) or virtio (`vtbd`) | the base device list and the root devices by GPT label |
| Display | a UEFI GOP framebuffer, 32 bits per pixel | vt_efifb through fbd as `/dev/fb0`; `surface_blit.hpp` assumes blue in the lowest byte, GOP's common BGRX order |
| Serial console | optional: COM1 at 0x3F8 | `loader.env.amd64`: `console=efi,comconsole`, `boot_multicons` |
| Clock | a battery clock (most boards); SNTP corrects it at boot | `appliance.conf` |

## Facts of the image

| Item | Value | Source |
|---|---|---|
| Root slot devices | `/dev/gpt/stxroota`, `/dev/gpt/stxrootb` (GPT labels, whatever the disk is) | `root-devices.gpt` |
| Loader's disk | `disk0` is the boot medium; other disks attached at power-on may come first | `loader.env.amd64` |
| vm.overcommit | not set: FreeBSD's default, 0 | no `sysctl vm.overcommit` in the image |
| Kernel cuts | the VM's option batches in amd64 spelling (INET6, DTrace, compat, NFS, MAC, AUDIT, RACCT, RCTL, KDB/DDB, ...) | `appliance/kernel/STXLIB-AMD64` |
| Package keys | none in the factory image | `image_payload.sh` |

## First boot: what the console (serial or screen) must show

1. `STXLOADER slot=A tries=0 fallback=0 reason=good`.
2. `STXINIT uptime_ns=`, then `STXSUPERVISOR boot slot=A tries=0 fallback=0`.
3. `(ED25519)`, then `STXNET dhcp <if> ok` for the board's NIC.
4. `STXSUPERVISOR devices ruleset=10 ...`.
5. After 60 s, `STXSUPERVISOR boot good slot=A`.
6. `ssh root@<address>` works with the owner's key.

## Checks per board

- **The boot medium is `disk0`.** With every disk of the board attached,
  the loader's slot line appears (a wrong `disk0` shows as a loader error
  and the unit falls back to `A` or stops). If another disk comes first,
  that board's rule is "only the appliance disk at power-on", or it gets
  its own `loader.env`.
- **The NIC.** `STXNET dhcp <if> ok` names an interface; if it says
  `no-ethernet-interface`, the board's NIC is not in GENERIC (or needs
  firmware, which the image does not carry).
- **The framebuffer.** `/dev/fb0` exists, 32 bits deep. The drawing test
  target's red, green and blue bars are in that order on the screen.
- **Input.** USB keyboard and mouse as `/dev/input/event*`, group-owned by
  the foreground target. A PS/2 keyboard reaches evdev through atkbd and
  kbdmux (`kern.evdev.rcpt_mask`, default).
- **Power loss during a system update**, as for the Pi.

## Not covered in 1.0

Wi-Fi (no firmware in the image), sound, a second display, hybrid
graphics, boards without a GOP framebuffer (legacy VGA only).
